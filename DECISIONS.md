# PrepPilot — Decision Log

Decisions resolved before implementation began, from a full read of the 18 documents
in [`docs/`](docs/). Each entry records the decision and the reasoning, so the
rationale is not buried in chat history.

Status legend: **Locked** — agreed, implement against it. **Pending** — awaiting input.

## 2. Architecture

| #   | Question                                                            | Decision                                                                                                     | Why                                                                                                                                                      |
| --- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D7  | Local database, explicitly deferred by PRD §28 and `TECH_STACK.md`. | **`expo-sqlite` + Drizzle ORM**, with a hand-written sync layer.                                             | Best Expo compatibility, full SQL control for the sync queue, typed queries, and no third-party sync vendor in the critical path.                        |
| D8  | Repository shape.                                                   | **pnpm monorepo**: `apps/mobile`, `apps/web`, `packages/shared`, `supabase/`.                                | Lets the progress engine and design tokens be shared verbatim between the app and the web demo — the same numbers and the same colours, by construction. |
| D9  | The "secure backend/API layer" required by PRD §15.                 | **Supabase Edge Functions.**                                                                                 | Supabase is already the backend; a second deployable service would add operational surface for no benefit.                                               |
| D10 | Build target.                                                       | **EAS development builds** from day one.                                                                     | Google Sign-In, Focus Mode and reliable exact alarms all require native modules unavailable in Expo Go.                                                  |
| D11 | Test tooling.                                                       | **Vitest** for `packages/shared` and the web app; **Jest + React Native Testing Library** for `apps/mobile`. | The React Native Jest preset cannot run a pure-TypeScript package cleanly, and vice versa. Splitting by package is standard for this monorepo shape.     |

## 3. Data model and synchronisation

`DATA_MODEL.md` describes the entities but omits several fields that offline-first
synchronisation cannot work without. These are additive.

| #   | Question                                                                                | Decision                                                                                                | Why                                                                                                                                                                                     |
| --- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D12 | Deletes. The documented model has no tombstones.                                        | **Soft deletes** via `deleted_at` on every synchronised table.                                          | Without a tombstone, a row deleted offline is resurrected by the next pull, because the client cannot distinguish "deleted here" from "not yet seen".                                   |
| D13 | Identifier generation. PRD §22 requires "stable IDs" without saying who mints them.     | **Client-generated UUIDv7.**                                                                            | Offline creation must produce a final ID immediately, with no server round-trip. v7 is time-ordered, which keeps B-tree index locality far better than v4.                              |
| D14 | Conflict resolution. PRD §22 requires "deterministic" resolution but names no strategy. | **Field-level last-write-wins** on `updated_at`, with `topics.completed` resolving to _completed wins_. | Row-level LWW discards concurrent edits to unrelated fields. Biasing completion toward "done" avoids the worst failure mode: silently un-checking work a student has actually finished. |
| D15 | Ordering. No position field is documented.                                              | **`position` column** on subjects, chapters and topics.                                                 | Syllabus order is meaningful, especially for imported templates where chapter sequence follows the official curriculum.                                                                 |
| D16 | Study sessions when their subject is deleted.                                           | **Preserved**, with denormalised name snapshots.                                                        | Cascading would retroactively shrink "total time studied using PrepPilot" (PRD §12) — the app would appear to lose the student's history.                                               |
| D17 | `study_sessions.status` values, undefined in the docs.                                  | `running \| paused \| completed \| abandoned`.                                                          | `abandoned` is needed for sessions interrupted by an app kill.                                                                                                                          |
| D18 | `reminders.repeat_rule` format, undefined in the docs.                                  | **Simple enum**, not RRULE.                                                                             | PRD §16 describes only title/date/time/repeat. Full RRULE is unnecessary complexity for scheduling local notifications.                                                                 |

## 4. Behaviour and presentation

| #   | Question                                              | Decision                                                                                                                                                       | Why                                                                                                                                                                                               |
| --- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D19 | Progress display when there are no topics to measure. | Render **`—`**, never `0%`.                                                                                                                                    | PRD §10 requires an "appropriate empty state rather than misleading progress". An untouched chapter and an empty chapter are different states and must look different.                            |
| D20 | Rounding of displayed percentages.                    | Never round up to `100%` while work remains, nor down to `0%` once work has started.                                                                           | A student at 99.99% seeing "100%" is a correctness bug in the product's core promise. Implemented in `formatPercent`.                                                                             |
| D21 | Timer behaviour when backgrounded or killed.          | Elapsed time **derived from stored timestamps**, not a live counter.                                                                                           | Survives process death without an Android foreground service and a custom native module.                                                                                                          |
| D22 | Focus Mode scope.                                     | DND toggle, usage monitoring with a warning overlay, full-screen focus timer, and suppression of PrepPilot's own notifications. Limitations documented in-app. | Android cannot block arbitrary apps without an AccessibilityService or device-admin privileges, both restricted by Play Store policy. PRD §17 explicitly forbids claiming universal app blocking. |
| D23 | Pomodoro defaults.                                    | 25 / 5, long break 15 after 4 cycles, auto-start off, all configurable.                                                                                        | Standard Pomodoro; PRD §11 does not specify values.                                                                                                                                               |
| D24 | Theme.                                                | **Dark by default**, with a light scheme defined from the start.                                                                                               | Every supplied reference screenshot is dark, and a study timer is often used at night. Both schemes are defined together so no token can exist in only one theme.                                 |

## 5. Security and accounts

| #   | Question                                                                                                                                                             | Decision                                                                                                                 | Why                                                                                                                                                                                      |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D25 | Templates: Supabase table or bundled?                                                                                                                                | **Bundled as JSON in the app.** Supabase stores only `user_template_imports`.                                            | `DATA_MODEL.md` places `templates` in Supabase, which would make template import require connectivity — contradicting the offline-first requirement.                                     |
| D26 | Phone OTP. PRD §7 requires it and the success matrix marks it Critical, but Supabase phone auth needs a paid SMS provider and, for Indian numbers, DLT registration. | **Built end-to-end**, credentials supplied later. Feature-flagged so the untested path cannot reach production silently. | Keeps the requirement satisfiable without blocking on a billing decision.                                                                                                                |
| D27 | Multiple sign-in methods for one person.                                                                                                                             | **Separate identities** (Supabase default) unless linking is requested.                                                  | Automatic linking by email is a known account-takeover vector and was not requested.                                                                                                     |
| D28 | Account deletion.                                                                                                                                                    | **Supabase Edge Function** using the service-role key; immediate hard delete of cloud and local data.                    | The client SDK cannot delete an auth user; only the admin API can.                                                                                                                       |
| D29 | Gemini model and cost control.                                                                                                                                       | `gemini-2.5-flash`, proxied server-side, with per-user rate limits from day one.                                         | The proxy spends the project owner's API key, so an unauthenticated or unlimited endpoint is a financial liability as much as a security one. PRD §15 requires the key stay server-side. |

## 6. Build tooling

Decisions forced by the toolchain rather than the specification, recorded because
they are non-obvious and easy to undo by accident.

| #   | Question                                      | Decision                                               | Why                                                                                                                                                                                          |
| --- | --------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D30 | `node_modules` layout.                        | **`nodeLinker: hoisted`** in `pnpm-workspace.yaml`.    | Expo's Metro bundler cannot resolve transitive dependencies through pnpm's default isolated store — `@expo/metro-runtime` fails to find `whatwg-fetch`. Verified by an Android bundle in CI. |
| D31 | Import specifiers inside `@preppilot/shared`. | **Extensionless** (`./progress`, not `./progress.js`). | The package is consumed as TypeScript source by three different bundlers. Vitest and Metro accept `.js` specifiers that resolve to `.ts`; Jest does not. Extensionless works in all three.   |
| D32 | `verifyDepsBeforeRun`.                        | **Disabled.**                                          | pnpm re-runs `install` before every script, which deadlocks on its own store lock in this workspace. CI installs with `--frozen-lockfile`, so lockfile drift is still caught.                |

## 7. Refinements made during implementation

| #   | Decision                                                                                                                                                                       | Why                                                                                                                                                                                                                                                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D33 | **D14 refined.** Field-level last-write-wins is implemented as a row-level `updated_at` plus a dedicated `completed_changed_at` on topics, rather than a timestamp per column. | Completion and naming are the only two fields on a row that a student realistically changes independently on two devices. A timestamp per column would triple the schema width for conflicts that cannot occur. Renaming a topic on one device must not revert a tick made on another, and this is the minimum that guarantees it. |
| D34 | Repository tests run the **generated migration** against in-memory SQLite (better-sqlite3), not a mock.                                                                        | Both drivers are synchronous Drizzle cores, so the tests execute the SQL the app ships — constraints, cascades, indexes and ordering included. A mock would only ever agree with whatever the code already does.                                                                                                                   |
| D35 | Deleting a subject tombstones the subject alone, not its chapters and topics.                                                                                                  | Descendants are reachable only through their subject, and the reads filter on it, so they disappear immediately. Tombstoning the whole tree would produce a large sync payload for what the student experiences as deleting one thing.                                                                                             |

| #   | Decision                                                                                                              | Why                                                                                                                                                   |
| --- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| D36 | A study session is written when the timer **starts**, then updated by a heartbeat every 30 seconds.                   | Writing only on stop loses the whole sitting if the app is killed. A heartbeat costs one small write per half-minute and caps the loss at 30 seconds. |
| D37 | Sessions carry **no foreign key** to subjects, chapters or topics — only ids plus a snapshot of the names.            | A cascade would shrink "total time studied using PrepPilot" retroactively (D16). The name snapshot keeps history readable after a rename.             |
| D38 | Pomodoro **breaks are not recorded** as study time.                                                                   | Counting them would inflate the total study figure and make it meaningless.                                                                           |
| D39 | `abandoned` sessions **count toward** total study time, and end at their last heartbeat rather than at recovery time. | The student really did that work, so dropping it would make the total a lie; but the hours the app spent closed were not studying.                    |

| #   | Decision                                                                                                                              | Why                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D40 | **Demo mode**, enabled only by `EXPO_PUBLIC_DEMO_MODE=true`, runs the app against local storage with a fixed account and no Supabase. | The app cannot be reviewed at all without a Supabase project, and none exists yet. This is a preview affordance, not a product feature: it is off unless the flag is exactly `"true"`, it never enables any other unprovisioned feature, and a banner on every screen says the session is local and unauthenticated so it cannot be mistaken for real synced data. It knowingly bypasses D1 for that one purpose. |
| D41 | Running sessions are **excluded** from the dashboard and history until they settle.                                                   | A running session has no final duration, so including it would make today's total climb as the timer advances and put a half-finished row in history.                                                                                                                                                                                                                                                             |
| D42 | `.wasm` added to Metro's asset extensions.                                                                                            | `expo-sqlite` runs in the browser through wa-sqlite, which ships as a `.wasm` file Metro does not treat as an asset by default. Without this the app cannot build for web at all.                                                                                                                                                                                                                                 |

| #   | Decision                                                                             | Why                                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D43 | Reminders are **local notifications only**; no push infrastructure.                  | PRD §16 describes alarms a student sets for themselves. Local scheduling needs no server, no credentials, and works offline.                                                                                             |
| D44 | Each reminder stores the platform notification id that currently backs it.           | Cancelling by id lets an edit or a disable target exactly one notification. Clearing everything the app scheduled would take out unrelated reminders, and scheduling without cancelling first produces duplicate alerts. |
| D45 | The notification id is **not** synced, and setting it does not mark the row pending. | The id is meaningful only on the device that created it.                                                                                                                                                                 |
| D46 | `weekdays` repeats are re-armed by the app on each launch.                           | Neither platform has a weekday-only trigger. The composer says so rather than implying an OS-level repeat.                                                                                                               |
| D47 | Permission is requested when the student first opens the composer, not at launch.    | The request then has obvious context. A refusal is surfaced on the screen instead of silently producing reminders that never fire.                                                                                       |

| #   | Decision                                                                                                                                                                                                                        | Why                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D48 | **D22 delivered as:** a full-screen countdown, PrepPilot's own notifications silenced, the screen kept awake, and a count of how often the student left the app. DND toggling and app-usage monitoring are **not** implemented. | Both need permissions no Expo module exposes — `ACCESS_NOTIFICATION_POLICY` and `UsageStatsManager` — which would mean a custom native module and, for blocking, privileges Play Store policy restricts. |
| D49 | Focus Mode counts departures instead of preventing them.                                                                                                                                                                        | Android does not let one app block another. Counting is the honest substitute: PrepPilot cannot stop someone switching away, but it can notice and show them afterwards.                                 |
| D50 | The capability list is **rendered in the app**, marking blocking and DND as unsupported.                                                                                                                                        | PRD §17 requires documenting device limitations and forbids claiming universal app blocking. A limitation buried in a file nobody reads is not documentation.                                            |

| #   | Decision                                                                                                                 | Why                                                                                                                                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D51 | Templates ship with **example content only**, every entry marked `verified: false` with its source shown on the preview. | No verified syllabus data has been supplied. A template claiming to be the JEE syllabus while being an approximation would mislead a student planning months of study around it. The import flow, preview and counts all work — adding real content is a data change to one file. |
| D52 | An imported syllabus is **ordinary data**, not marked as template-derived.                                               | PRD §13 requires imported templates stay fully editable. Tagging rows would invite behaviour that fights a student renaming or deleting part of their own syllabus.                                                                                                               |
| D53 | Account deletion removes **local data only** and says so. The cloud step is not built.                                   | Deleting a Supabase auth user needs a service-role Edge Function (D28), which cannot exist without a Supabase project. Reporting a full deletion that never reached a server would be a false claim about someone's personal data.                                                |
| D54 | Deletion requires typing `DELETE`.                                                                                       | Destroying months of study history should take more than two taps in the same place.                                                                                                                                                                                              |

| #   | Decision                                                                                                        | Why                                                                                                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D55 | An AI reply can only ever **propose**; the proposal grammar has no verb for deleting, completing or reordering. | PRD §14 forbids the assistant changing the tracker on its own. Enforcing it in the data shape makes it structural rather than a promise in a prompt the model might ignore.                                                                            |
| D56 | A proposal over 200 topics is refused rather than applied.                                                      | Confirming hundreds of topics is a rubber stamp, not the review §14 requires.                                                                                                                                                                          |
| D57 | The Gemini proxy never forwards an upstream error body.                                                         | A Gemini failure can carry key or quota detail. Failures are replaced with a generic student-facing message.                                                                                                                                           |
| D58 | Modal backdrops are **siblings** of their sheet, not parents.                                                   | A backdrop that wraps its content and carries `accessibilityRole="button"` makes a screen reader announce the whole dialog as one button whose name is every word inside it. Every modal in the app had this shape; all now use one `Sheet` primitive. |

## 8. Design system

| #   | Decision                                                                                                        | Why                                                                                                                                                                                                                                            |
| --- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D59 | **NativeWind**, not Tailwind CSS.                                                                               | Tailwind is a CSS framework and React Native has no CSS engine, so Tailwind itself cannot run here. NativeWind provides the identical authoring model compiled to RN styles. Verified against Expo SDK 57 before adopting.                     |
| D60 | The Tailwind theme **restates** the design tokens rather than importing them, with a test asserting they match. | A Tailwind config is plain JavaScript loaded by the build; reaching into a TypeScript module from it only works while the toolchain happens to strip types. Restating it is honest about that, and the test makes drift fail rather than ship. |
| D61 | **Inter**, loaded before first paint.                                                                           | The platform default faces differ between Android and the browser, so identical type would render differently on each. Inter also has tabular figures, without which the timer and every percentage visibly jitter as digits change width.     |
| D62 | Motion is short — 90–320ms — and the press scale is 0.97.                                                       | Past roughly 250ms a tap response reads as lag rather than polish. The scale responds on touch-down, so the interface feels immediate even when the work behind it is not.                                                                     |
| D63 | Elevation is restrained; only primary actions and un-nested cards lift.                                         | On a dark surface a heavy shadow reads as grime. If everything is elevated, nothing reads as the main thing to do.                                                                                                                             |
| D64 | Content caps at 720px and centres.                                                                              | The app runs in a browser and on tablets, where full-width text lines stretch far past the measure at which reading measurably slows.                                                                                                          |
| D65 | The seven-day chart anchors its scale to **at least one hour**.                                                 | Scaling purely to the largest bar made a twelve-second session fill the chart, which reads as a full day of study.                                                                                                                             |
| D66 | Skeletons replace spinners where the eventual shape is known.                                                   | A skeleton holds the layout still, so nothing jumps when content arrives, and communicates _what_ is coming rather than only that something is.                                                                                                |

## 9. Synchronisation

| #   | Decision                                                              | Why                                                                                                                                                                                                                            |
| --- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D67 | Sync **pulls and merges before pushing**.                             | Pushing first overwrites the server with a local row that has not been reconciled, destroying any change made elsewhere since the last sync. Caught by a test: a local rename silently reverted a tick made on another device. |
| D68 | A **tombstone always wins** a conflict, and the earliest one is kept. | Resurrecting something a student deleted is worse than losing an edit they made to it.                                                                                                                                         |
| D69 | A dead heat on completion resolves to **completed**.                  | If both clocks genuinely agree, marking work done is the safer error. Silently un-ticking finished work is the failure a student would never forgive.                                                                          |
| D70 | The local copy wins an **exact** tie on `updatedAt`.                  | Otherwise a device rewrites rows it already agrees with, on every pass, forever.                                                                                                                                               |
| D71 | The watermark is rewound by **60 seconds** on each pull.              | Device and server clocks differ, so a row written just before the last sync can carry an earlier timestamp. Re-pulling a minute of seen rows is free — every write is an idempotent upsert — and missing one is not.           |
| D72 | The watermark advances **only on success**.                           | A failed pass must be retried in full rather than skipping whatever it never reached.                                                                                                                                          |
| D73 | Migrations **grant** table privileges explicitly.                     | RLS filters rows only after the privilege check passes, so a table with policies but no grant rejects every request outright. Both migrations had this bug; only running them against a real Postgres revealed it.             |
| D74 | `notification_id` and `sync_status` never leave the device.           | The first identifies a scheduled notification on one device (D45); the second is that device's own bookkeeping.                                                                                                                |

| #   | Decision                                                                                                     | Why                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D75 | Connectivity prefers `isInternetReachable` over `isConnected`, and assumes **online** when neither is known. | Being attached to an unpaid café wifi is "connected" and useless. Where the platform knows nothing, wrongly blocking a connected student is worse than a request that fails and retries. |
| D76 | Sync retries automatically on the **transition** back online, not on every network report.                   | PRD §22 asks for retry after failure; waiting for the student to notice is not that. Firing on every report would re-sync when wifi merely switches to cellular.                         |
| D77 | A sync attempted while offline returns quietly instead of failing.                                           | Failing loudly on every launch in a tunnel trains a student to ignore the message. The reconnect watcher retries as soon as there is a connection.                                       |
| D78 | The offline banner reassures rather than alarms.                                                             | Everything except the assistant works offline (PRD §6), so the message says what is still true rather than implying something is broken.                                                 |
